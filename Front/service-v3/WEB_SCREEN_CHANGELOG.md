# Service V3 웹 화면 수정 이력

작성일: 2026-09-16  
범위: `PUBLISH/Front/service-v3/` 및 서비스 V3 진입 링크가 추가된 `PUBLISH/Front/index.html`

## 1. 작업 목적과 기준

- 기존 퍼블리싱 파일을 독립 실행 가능한 `service-v3` 폴더로 구성했다.
- 해비치 디자인 의견 PDF의 문구, 색상 역할, 공통 여백, 반경, 화면 구성을 반영했다.
- PDF의 숫자 주석은 적용 기준값이며, 화면 원본 PNG의 픽셀 색을 그대로 뜻하지 않는다는 점을 전제로 검토했다.
- 폰트 크기는 PDF 값으로 일괄 축소하지 않고 기존 모바일 화면의 크기를 유지했다. 대신 PDF의 정보 위계를 참고해 굵기를 조정했다.

## 2. 폴더와 진입 구조

### 완료

- `service-v3` 내부에서 HTML, CSS, JS, 폰트, 로고, 아이콘, 메뉴 이미지를 모두 참조하도록 경로를 정리했다.
- 해비치 디자인 의견 폴더의 이미지를 직접 참조하지 않고 다음 로컬 자산을 사용한다.
  - `resources/images/brand/` — 해비치 제공 `브랜드 로고.png`를 그대로 반입
  - `resources/images/icon/` — 해비치 제공 Bottom Navigation 아이콘 형태 반영 (아래 12장 참고)
  - `resources/images/menu/`
- 모든 자산 참조는 HTML 기준 상대경로 `resources/...`로 통일했다.
- `Front/index.html` 최상단에 최종본 영역을 만들고 아래 화면으로 바로 이동할 수 있게 연결했다.
  - 로그인/회원가입: 스플래시, 로그인, 회원가입, 비밀번호 재설정
  - 식단: 홈, 식단 상세
  - 의견: 접수, 내역
  - 공지 및 알럿: 공지, 공지 상세, 공지 팝업, 일반 알럿
  - My 및 설정: My, 비밀번호 변경, 약관, 개인정보처리방침, 앱 버전, 회원 탈퇴

### CAS 회사 테마 CSS 생성·적용 기준

회사별 테마는 임의의 화면별 CSS를 만드는 방식이 아니라, CAS가 보유한 **회사 대표색 한 값**으로 테마 파일을 생성·선택하는 구조다. 서비스 공통 CSS가 그 한 값을 바탕으로 파생색을 계산하므로, 새 회사를 추가해도 각 컴포넌트의 색상을 별도로 수정하지 않는다.

```css
/* CAS 또는 앱 셸이 회사 코드 기준으로 생성·연결하는 파일의 최소 형태 */
/* resources/css/theme-{company-code}.css */
:root {
  --brand-primary: <CAS의 회사 대표색>;
}
```

| 구분 | 책임 | 현재 퍼블리싱 반영 범위 |
| --- | --- | --- |
| CAS/관리자 | 회사 코드와 대표색을 관리하고 `theme-{company-code}.css`를 생성하거나 동등한 CSS 변수를 앱 셸에 주입 | 연동 명세 대상. 이 정적 퍼블리싱 폴더에는 CAS API가 없음 |
| 앱 셸/서버 | 로그인 세션의 회사 코드에 맞는 테마 파일을 연결 | 운영 연동 대상 |
| `service.css` | `--brand-primary`를 받아 파생색·공통 컴포넌트 색을 계산 | 구현 완료 |
| `theme-haevichi.css` | 해비치 초기값 `--brand-primary: #70747A`만 제공 | 구현 완료 |
| `common.js` | `?theme=haevichi`일 때 해비치 테마 파일을 연결하는 검토용 스위처 | 데모 전용. CAS 연동 로직이 아님 |

파생 토큰의 계산식은 다음과 같다. 일반 카드·본문·입력선은 브랜드색과 무관한 중립 토큰을 사용하고, 선택·CTA·약한 강조처럼 브랜드 영향이 필요한 부분만 이 값을 사용한다.

| 토큰 | 계산식 | 역할 |
| --- | --- | --- |
| `--brand-primary` | CAS 대표색 | 선택 상태, 주요 CTA, 필독 배지 |
| `--brand-primary-light` | `color-mix(in srgb, primary 56%, white)` | 보조 강조·전환용 파생색 |
| `--brand-primary-bg` | `color-mix(in srgb, primary 7%, #FEFFFF)` | 공지 바, 주요 공지, 약한 강조 배경 |
| `--brand-primary-border` | `color-mix(in srgb, primary 32%, #D5DAE0)` | 브랜드 연계 테두리가 필요한 경우 |
| `--brand-primary-pressed` | `color-mix(in srgb, primary 88%, #171A1F)` | 주요 버튼 누름 상태 |

**해비치 보정 검증:** `#70747A`를 입력하면 `--brand-primary-bg`가 `#F4F5F6`으로 계산된다. 이는 PDF에서 공지 Bar 및 홈 11번 배경으로 제시된 연한 회색 계열과 일치하도록 혼합 비율·혼합 대상색을 보정한 결과다. 즉 `#F4F5F6`을 고정으로 넣은 것이 아니라, 해비치 회색을 기준으로 이 결과가 나오게 설계한 것이다. 다른 회사에서는 같은 명도 관계로 다른 색조가 계산된다.

### 해비치 PDF 분석 기준

분석 원본: `해비치 디자인 의견/20260915/1. APP_기준 설정.pdf`

PDF의 화면 이미지는 원본 PNG이고, 번호·연결선·설명은 SVG 주석으로 별도 덧씌워진 문서다. 따라서 다음 우선순위로 적용 여부를 판단했다.

1. 번호별 설명의 색상·반경·패딩·상태값은 적용 기준으로 사용한다.
2. 화면 PNG는 요소의 존재, 상태 구분, 배치 관계를 확인하는 기준으로 사용한다. PNG를 픽셀 단위 실측값으로 간주하지 않는다.
3. PDF의 폰트 크기는 적용 기준값이지만, 이번 A안에서는 모바일 가독성을 위해 기존 소스의 크기를 유지한다. 따라서 크기 불일치는 의도된 보류이며, 굵기 위계만 PDF를 참조해 조정했다.
4. PDF 설명과 화면 이미지가 충돌하거나, 예를 들어 홈 11번의 `BG #F4F5F6`처럼 적용 범위가 명확하지 않은 경우에는 임의 확장 적용하지 않고 확인 사항으로 남긴다.

PDF에서 확인한 공통 기준은 `Padding 20px`, `Base Grid 4px`, `Surface #FFFFFF`, 입력창 R10, 카드 R16, 주요 버튼 R26이다. 단, Base Grid는 토큰 단위 기준이며 모든 실제 여백을 기계적으로 4의 배수로 바꾸라는 의미로 해석하지 않았다.

| PDF 분석 항목 | PDF에서 읽은 역할 | 소스 반영 원칙 |
| --- | --- | --- |
| 회사 대표색 | 선택 상태·주요 CTA·필독 배지에 쓰이는 해비치 회색 `#70747A` | `--brand-primary` 한 값으로 받고 회사별로 교체 |
| 연한 대표색 | 공지 Bar·주요 공지의 약한 강조 배경 | `--brand-primary-bg`를 동적으로 계산. 해비치에서 `#F4F5F6` |
| 서비스 블루 | 제목·완료 상태에 쓰이는 `#156AAF` | 회사 테마와 분리한 고정 `--service-primary-blue` |
| 중립 UI | 본문·보조·선·카드에 `#171A1F`, `#4B525A`, `#8C95A1`, `#D5DAE0`, `#E6E9ED`, `#FFFFFF` | 고정 중립 토큰. 대표색 변경의 영향을 받지 않음 |
| 선택 상태 | 날짜·식사 탭·주요 버튼은 진한 대표색/흰 글자 | `--brand-primary` / `--ui-surface` 조합 |
| 비선택·비활성 상태 | 비선택 날짜는 투명, 일반 탭은 중립 배경, 비활성 버튼은 중립선 | 브랜드색을 불필요하게 확장하지 않고 중립 토큰 사용 |

### 공통 규칙

- 서비스·인증 화면의 좌우 패딩은 20px로 정리했다.
- 기본 간격 토큰은 4px 단위(`4/8/12/16/20/24px`)로 제공한다. 개별 화면의 모든 간격을 강제로 4의 배수로 변경하지는 않는다.
- 입력창 R10, 카드 R16, 주요 버튼 R26, 공통 표면 `#FFFFFF`를 사용한다.
- 하단 네비게이션은 홈 / 나의 의견 / 공지 / My 4개 항목으로 통일했다.
- 공통 서비스 CSS는 `resources/css/service.css`, 인증 화면 전용 CSS는 `resources/css/auth.css`로 분리했다.

## 4. 인증 화면

### 스플래시 (`splash.html`)

- 브랜드 메시지는 화면 중앙, 브랜드 로고는 화면 하단에 배치했다.
- 좌우 패딩 20px, 흰색 표면, 4px 그리드 기준을 반영했다.
- 캡처 검토용으로 일시 중지했던 자동 로그인 이동은 다시 활성화했다.

### 로그인 (`login.html`)

- 로그인 화면에서 로고 이미지를 제거했다.
- `오늘의 한끼를 만나보세요.` 문구, 입력창, 자동로그인/비밀번호 찾기, 로그인 버튼, 회원가입 링크의 위치를 가이드에 맞춰 정리했다.
- 사내 메일/비밀번호 입력 전에는 비활성 버튼, 필수값 입력 후에는 활성 버튼으로 구분되게 했다.

### 회원가입 (`signup.html`)

- 상단 로고, 1~4단계 진행 표시, 메일 안내/입력/동의/버튼/이전 링크를 공통 인증 기준으로 정리했다.
- 메일 주소 수집 단계와 추가 정보 수집 단계에 개인정보 수집·이용 동의를 각각 둔다.
- 추가 정보에서 직급을 제거했다.
- `소속 구분`은 한 줄 전체 폭, `성별`과 `연령대`는 한 줄 2열 배치로 구성했다.
- 동의 영역과 다음 버튼 사이의 여백을 보완했다.
- 입력·동의 완료 전후의 다음 버튼 색을 명확히 구분했다.

### 비밀번호 재설정 (`password-reset.html`)

### 1번 후속 — 아이콘 지정 방식 자체를 변경 (2026-09-16)

경로만 고쳤을 때도 하단 탭 아이콘이 노출되지 않아, 원인을 지정 방식으로 좁혀 구조를 바꿨다.

- 기존: HTML 인라인 `style="--icon:url(...)"` → `style.css`의 `.tabbar .icon{ mask-image:var(--icon) }`가 받는 구조.
  커스텀 속성 안의 상대경로는 **선언된 위치 기준**으로 해석되는데, 인라인 style의 기준은 HTML 문서라서
  `style.css`가 전제한 `../images/` 기준과 어긋난다. 두 기준 중 어느 쪽에 맞춰도 다른 쪽에서 깨지는 구조였다.
- 변경: 인라인 변수를 제거하고 `service.css`에 `.tabbar .icon-home / .icon-voc / .icon-notice / .icon-my`로
  `mask-image`를 직접 선언했다. `service.css`는 `resources/css/`에 있으므로 `../images/icon/…`의 해석 기준이
  한 곳으로 고정된다.
- 함께 처리: 아이콘 SVG에 `width="24" height="24"`를 추가해 고유 크기를 갖게 했다.
  viewBox만 있는 SVG는 렌더러에 따라 `mask-size:contain` 계산이 0으로 잡힐 수 있다.
- 색은 계속 `currentColor`가 담당하므로 활성/비활성 파일 분리는 여전히 필요 없다.
- 캐시 버전을 `?v=20260916-26`으로 올렸다. 단 HTML 자체에는 버전이 없으므로 **강제 새로고침이 필요**하다.

### 1번 후속 2 — file:// 직접 실행 시 아이콘 미노출 (2026-09-16)

로컬 서버(검토용 패널)에서는 보이는데 HTML 파일을 그대로 더블클릭해서 열면(`file://`) 아이콘이 보이지 않았다.

- 원인: CSS `mask`는 `background-image`와 달리 **동일 출처 제한**을 받는다. `file://`에서는 각 파일이
  서로 다른 출처로 취급되므로 외부 `.svg`를 `mask-image`로 쓰면 차단되고 아이콘이 통째로 사라진다.
  경로 문제가 아니라 프로토콜 문제이므로, 경로를 어떻게 고쳐도 `file://`에서는 해결되지 않는다.
- 조치: 하단 탭 아이콘 4개의 `mask-image`를 `service.css` 안에 **data URI로 인라인**했다.
  data URI는 이 제한을 받지 않아 `file://`과 로컬 서버 모두에서 동일하게 보인다.
- 함께 처리: 마스크로 쓸 때 색이 의미가 없고 `currentColor`가 빈 마스크로 계산될 여지를 없애기 위해
  아이콘 4개의 `stroke`를 `#000`으로 고정했다. 화면에 보이는 색은 계속 CSS의 `currentColor`가 정한다.

## 14. 식단 상세 대표 이미지 원본 비율 적용 (2026-09-16)

홈 카드만 원본 비율 유지로 바꾸고 식단 상세는 누락돼 있었다. PDF 식단 상세 02번 주석은
`대표 식단 이미지 — 원본 비율 유지 · Surface #FFFFFF`이므로 상세도 적용 대상이다.

- 증상: `style.css`의 `.hero{ aspect-ratio:16/10 }` + `.hero img{ object-fit:cover }`가 그대로 남아
  16:10으로 고정 크롭되고 있었다. `service.css`에 `.hero` 재정의가 없었다.
- 영향: 중식 원본은 1672x941(1.78:1)이라 거의 잘리지 않지만, 조식·석식 원본은 1254x1254(1:1)이라
  **세로가 38% 잘렸다.** 끼니에 따라 크롭 정도가 달라 보이던 원인이다.
- 조치: `service.css`에 `.menu-detail-card .hero{ aspect-ratio:auto }`,
  `.menu-detail-card .hero img{ width:100%; height:auto; object-fit:contain }`를 추가했다.
  홈 카드와 같은 규칙이다.
- 히어로 이미지 높이는 등록된 이미지의 비율을 그대로 따른다. 임의의 `max-height` 상한은 두지 않는다.
  원본 비율 유지는 확정 사항이며, 별도의 권장 비율을 두지 않는다.
- 캐시 버전 `?v=20260916-31`.

## 17. 대표색 위 글자색 자동 판정 (2026-09-16)

멀티테넌트 검증 중, 밝은 대표색에서 선택 상태의 흰 글자가 읽히지 않는 문제를 확인했다.
`#70747A`는 흰 글자 대비 4.70:1이지만 테스트용 `#39CC54`는 2.11:1로 기준(AA 4.5) 미달이다.

- `--brand-on-primary` 토큰을 도입하고 `service.css`의 대표색 배경 6곳이 이 값을 쓰도록 했다.
  선택 날짜 · 끼니 탭 · 접수/내역 탭 · 필독 배지 · 주요 버튼 · 확인 버튼.
- 값 결정은 두 경로다. 테마 파일이 지정하면 그 값(A), 없으면 `theme-oncolor.js`가 `L*`로 판정(B).
- 임계값은 `L* 55`다. 흰 글자와 `#171A1F` 글자의 대비 교차점이 `L* 52`이므로 그 근처에서
  대비가 높은 쪽이 선택된다. 55는 경계 부근을 흰 글자로 약하게 치우치게 한 값이다.
- 런타임 대비 비교 방식은 쓰지 않는다. 회색 계열은 두 대비가 모두 4 언저리라 결과가 쉽게 뒤집힌다.
- `theme-oncolor.js`는 `<head>`에서 테마 링크 뒤에 **동기 로드**한다. 본문 스크립트로 두면
  첫 페인트 이후 글자색이 바뀌어 화면이 튄다. 테마 링크 교체 시에는 `load`에서 다시 판정한다.
- **해비치 영향 없음.** `#70747A`는 `L* 48.7`로 A·B 어느 경로로도 `#FFFFFF`다.
- 인증 화면은 테마를 쓰지 않으므로 대상이 아니다.
- 캐시 버전 `?v=20260916-38`.
